    Getting Started

    A form is a menu that is shown to a player. It is made of elements (also called widgets), such as labels, buttons, text fields, and inventory slots, which are arranged by layout elements like gui.VBox. You describe a form with a build function, which is the function you pass to flow.make_gui(). It returns the elements, and flow works out the positions and sizes and shows the form for you. This documentation always calls it the build function. See Functional Elements for what each element does.

    Basic Example

    See example.lua in the flow repository for a more comprehensive example which demonstrates how layouting and alignment works.

    Try the example in game

    In singleplayer, a player with the server privilege can run /flow-example to open it in the game.

    The build function is called with the player and a context table (ctx) every time the form is drawn. ctx belongs to one player's copy of the form: flow keeps the same table for as long as the form is open, passes it to the build function and to every on_event function, and you can store anything in it. Flow adds a ctx.form table to it, which holds the current values of the form's named inputs (see Names and Values).

    Three things in the example below look alike but differ:

    Name in the example What it is Who writes it
    ctx.value The starting ctx: whatever you passed to form:show. You, before the form is shown.
    ctx.form.cool_dropdown The live value of the input named cool_dropdown. Flow: it sets the initial value on the first draw and updates it when the player changes the input.
    ctx.picked Your own state. Your on_event function, when the player presses the button.

    All three are in the same table.

    Do not use form as a ctx key

    Do not use form as a key of your own or replace ctx.form: flow raises an error if you do that in the build function.

    form:show(player, ctx) shows the form to a player. Flow uses the ctx table you pass as is (not a copy), or a new empty one if you leave it out. In a mod, get the player object from a chat command or core.register_on_joinplayer.

    local gui = flow.widgets -- local recommended for direct referencing
local STARTING_SELECTION = 3 -- change and rerun to see the difference

local function build_vbox(player_obj, ctx)
    return gui.VBox {
        gui.Label { label = "Here is a dropdown:" },
        gui.Dropdown {
            name = "cool_dropdown",
            items = { 'First item', 'Second item', 'Third item' },
            index_event = true,
            selected_idx = ctx.value or 1
        },
        gui.Button {
            label = "Get dropdown index",
            on_event = function(player, ctx)
                local idx = ctx.form.cool_dropdown or ctx.value or 1
                core.chat_send_player(player:get_player_name(),
                    ("You have selected item #%d!"):format(idx))

                -- Remember the index and redraw so the label below shows it.
                ctx.picked = idx
                return true
            end,
        },
        gui.Label {
            label = ctx.picked
                and ("You have selected item #%d!"):format(ctx.picked)
                or "Pick an item, then press the button.",
        },
    }
end

local form = flow.make_gui(build_vbox)
-- "singleplayer" is the default player name for single-player games
local player_obj = core.get_player_by_name("singleplayer")

form:show(player_obj, { value = STARTING_SELECTION }) -- Starting ctx, optional

    Pick an item and press the button: the button's on_event function stores the index in ctx.picked and returns true, which redraws the form so that the label under the button changes. The same message is also sent to the chat.

    Updating Forms

    If some data displayed inside a form changes (for example a timer or progress indicator), you can use my_gui:update(player) or my_gui:update_where(func) (see below) to update the form without resetting ctx or showing the form again if the player has closed it.

    Luanti has no way to change a form that is already open, so flow has to show the whole form again.

    Updates can discard typed text

    Because the whole form is shown again, players may lose text typed into fields that hasn't been sent to the server (which happens when they press a button or Enter) when the form is updated. See Names and Values.

    Here is a form with one button for each way to update it. The counter is a plain variable, not something stored in ctx, so flow cannot notice when it changes. Each button adds 1 to it and then redraws the forms that should show the new number.

    Example

    local gui = flow.widgets
local counter = 0 -- External state; flow cannot track its changes.
local my_gui

local function add_button(label, update)
    return gui.Button {
        label = label,
        on_event = function(player, ctx)
            counter = counter + 1
            update(player, ctx)
        end,
    }
end

my_gui = flow.make_gui(function(player, ctx)
    ctx.test = 123 -- Used by update_where() below.
    return gui.VBox {
        gui.Label { label = "Counter: " .. counter },
        add_button("Add 1 and update my form", function(p)
            my_gui:update(p)
        end),
        add_button("Add 1 and update forms with ctx.test == 123", function()
            my_gui:update_where(function(_, c) return c.test == 123 end)
        end),
        add_button("Add 1 and update forms of admins", function()
            my_gui:update_where(function(p)
                return core.check_player_privs(p:get_player_name(), "server")
            end)
        end),
        add_button("Add 1 and update everyone's form", function()
            my_gui:update_where(function() return true end)
        end),
    }
end)

    Inside an on_event handler, you can return true instead of calling my_gui:update(player), as the click counter example below does.

    HUDs and inventories

    If you're using a form as a HUD, you must call my_gui:show_hud(player) to update it. See HUDs for how to show and close one. Inventory forms are updated with set_as_inventory_for, see Inventory. The table in Ways to Redraw a Form compares all of them.

    Updating a form does not reset ctx. In this example a timer redraws every open copy of the form each second, while the click counter stored in ctx survives every redraw:

    local gui = flow.widgets
local seconds = 0 -- Shared by every open copy of the form.

local form = flow.make_gui(function(player, ctx)
    return gui.VBox {
        gui.Label { label = ("Form drawn after %d seconds"):format(seconds) },
        gui.Label { label = ("Clicks (kept in ctx): %d"):format(ctx.clicks or 0) },
        gui.Button {
            label = "Click me",
            on_event = function(player, ctx)
                ctx.clicks = (ctx.clicks or 0) + 1
                return true -- redraw this form
            end,
        },
    }
end)

local function tick()
    seconds = seconds + 1
    form:update_where(function() return true end)
    core.after(1, tick)
end
core.after(1, tick)

form:show(core.get_player_by_name("current_player"))

    Redrawing When a Value Changes

    You often do not need return true. If your build function reads the value of a named input from ctx.form, flow notices and redraws the form by itself whenever the player changes that value.

    local form = flow.make_gui(function(player, ctx)
    return gui.VBox {
        gui.Checkbox { name = "advanced", label = "Show advanced options", selected = true },

        -- Reading ctx.form.advanced here makes flow redraw the form
        -- whenever the checkbox changes.
        ctx.form.advanced and gui.Label { label = "Advanced options" }
            or gui.Nil {},
    }
end)

    The rules are:

    • Only reads while the build function runs count, including reads in helper functions that it calls. Reading ctx.form inside an on_event function does not.
    • The form is only redrawn if the value is different from the stored one.
    • If the element has its own on_event function, there is no automatic redraw. That function has to return true instead.
    • Text fields only send their text when the player presses a button or Enter (see Names and Values), so the redraw happens then, and only if the text is different from the stored one. Pressing a button with the text unchanged does not redraw because of the field.

    Here are the two cases that surprise people. Only Show details redraws the form when ticked:

    local form = flow.make_gui(function(player, ctx)
    return gui.VBox {
        -- No on_event, and the build function reads it below: ticking
        -- this redraws the form.
        gui.Checkbox { name = "details", label = "Show details" },

        -- Has its own on_event: ticking this does NOT redraw the form
        -- unless the function returns true.
        gui.Checkbox {
            name = "loud", label = "Loud",
            on_event = function(player, ctx) end,
        },

        gui.Label {
            label = ("details = %s, loud = %s"):format(
                tostring(ctx.form.details), tostring(ctx.form.loud)),
        },
    }
end)

    Context and Redraws at a Glance

    Context Lifetime by Mode

    How long ctx lives depends on how the form is shown:

    How the form is shown Where ctx comes from How long it is kept
    my_gui:show(player, ctx) The table you pass, or a new empty one. Until the form is closed. update, update_where and return true keep it. Calling show again starts with a new one.
    my_gui:set_as_inventory_for(player, ctx), see Inventory The table you pass. If you pass none and this form is already the player's inventory, the existing ctx is reused, otherwise a new empty one. Until the form is unset or the player leaves. Passing a new ctx replaces the old one.
    my_gui:show_hud(player, ctx), see HUDs The table you pass, or a new empty one every time. Not kept: flow remembers nothing between calls, so pass your own table each time.
    my_gui:render_to_formspec_string(player, ctx), see Rendering to a Formspec The table you pass, or a new empty one. Flow keeps nothing: pass the same ctx each time you redraw.

    Ways to Redraw a Form

    Way Redraws Keeps ctx Works for
    return true from on_event or on_key_enter The form of the player who used it Yes Forms shown with show and inventory forms
    Reading ctx.form.name in the build function (see Redrawing When a Value Changes) The form of the player who changed the value Yes Forms shown with show and inventory forms
    my_gui:update(player) One player, if they have the form open Yes Forms shown with show only
    my_gui:update_where(func) Every player with the form open for whom func(player, ctx) returns true Yes Forms shown with show only
    my_gui:set_as_inventory_for(player, ctx) One player Reused if you pass none Inventory forms only
    my_gui:show_hud(player, ctx) One player No HUDs only
    my_gui:show(player, ctx) One player (and the old form is replaced) No, starts from the ctx you pass Forms shown with show
